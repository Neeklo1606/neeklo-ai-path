## P0 — критичное

### 0.1 🔴 Прод: API не работает, и об этом никто не узнал автоматически
Все пути бэкенда (`/cms-api/*`, `/avito/*`, `/tg/*`, `/incoming/*`) отдают 502, статика работает. Значит: заявки с сайта не сохраняются, сообщения Avito не принимаются (агент молчит), чат и админка недоступны, блок кейсов пуст.

Падение не отслеживается ничем: в репозитории нет ни healthcheck-скрипта, ни внешнего мониторинга, ни алерта. Узнали случайно.

**Минимум:** внешняя проверка `https://neeklo.ru/cms-api/health` раз в минуту с уведомлением в Telegram. Для PM2 — `pm2-health` или cron-скрипт с `curl` и `pm2 restart` при двух неудачах подряд.

### 0.2 🔴 Утечка памяти в ограничителе запросов
`server/services/billing.service.mjs:36-48` — счётчики лимита хранятся в `Map`, ключ на каждый IP-хеш, **записи никогда не удаляются**: истёкшее окно перезаписывается, но ключ остаётся навсегда.

```js
const buckets = new Map();            // :37
b = { n: 0, resetAt: now + WINDOW_MS }; buckets.set(keyHash, b);  // :43-44
// buckets.delete — не вызывается нигде
```

При этом в `ecosystem.config.cjs:34` стоит `max_memory_restart: "400M"`. Любой скан ботами даёт десятки тысяч уникальных IP → память растёт → PM2 перезапускает процесс, обрывая запросы. **Это первый кандидат на причину сегодняшнего 502.** Починка: удалять просроченные ключи при обращении плюс периодическая чистка.

### 0.3 🔴 Исходный код сайта доступен всем
`vite.config.ts:25` — `sourcemap: true` в продакшен-сборке, карты отдаются наружу: `https://neeklo.ru/assets/index-57LtBGAz.js.map` → 200, 2.4 МБ. Видны все исходники, включая логику админки.

### 0.4 🔴 CORS открыт для любого сайта вместе с куками
`server/cms-server.mjs:188` — `cors({ origin: true, credentials: true })`. Любой домен получает доступ к API от имени посетителя. Кука чата закрыта флагами `HttpOnly; SameSite=Lax` (`:228-241`), это смягчает, но список доменов нужен.

### 0.5 🔴 Любая `console.error` уходит в Telegram
`server/cms-server.mjs:5143-5155` подменяет `console.error` и шлёт текст во все одобренные чаты. В сообщение может попасть строка подключения к БД, токен или данные клиента. При массовом сбое — лавина сообщений.

### 0.6 🔴 18 высоких уязвимостей в зависимостях
`react-router` 6.30.1 (XSS через открытые редиректы), `axios`, `form-data` (CRLF-инъекция), `lodash`, `@prisma/config`. Все чинятся обновлением. Отдельно `multer` 1.x — ветка снята с поддержки.

### 0.7 🔴 В репозитории зашит админ по умолчанию
`prisma/seed.mjs:11-13` — `dsc-23@yandex.ru` / `123123123` / роль ADMIN, если переменные окружения не заданы. Если seed когда-либо запускали на проде, учётка существует с этим паролем. Проверить `app_users` на проде и сменить пароль.

## P1 — функциональные ошибки

### 1.1 🟠 Сохранение настроек стирает признак «публичная» (воспроизведено)
`server/cms-server.mjs:1892-1911` — `PATCH /settings/:key` всегда пишет `isPublic: !!req.body.is_public`. Кто сохраняет без этого поля, делает ключ непубличным. Проверка на живом API:

```
PATCH kp.showcase {"value":…,"is_public":true} → /settings/public: {"kp.showcase":{…}}
PATCH kp.showcase {"value":…}                  → /settings/public: {}
```

Из-за этого раздел админки «Страницы сайта» (`AdminSitePagesPage.tsx:74`) пишет ключи `page.*`, которые тут же пропадают из `/settings/public` — а читает он именно оттуда. Проверено: после сохранения ключ `page.home.h1` в публичных настройках отсутствует. Тот же механизм ломает витрину `/kp`, если её сохранить без галочки.

### 1.2 🟠 Два мёртвых дубля маршрутов настроек
`server/cms-server.mjs:5084` и `:5098` повторно объявляют `GET /settings` и `PATCH /settings/:key`. Express использует первые (`:1883`, `:1892`), поздние недостижимы — но хранят значение иначе и не трогают `isPublic`. Правка «не того» обработчика ничего не изменит: ловушка при работе с настройками.

### 1.3 🟠 Девять разделов админки обращаются к несуществующим эндпоинтам
Блог, видео, регламенты, база знаний (статьи), CRM-дашборд, контакты, сделки, статистика дашборда — обработчиков нет ни в коде, ни в истории git. Публичный сайт задет: вкладка «Видео» на `/cases` всегда пустая, блог показывает статьи из `src/data/news.ts`. Таблицы `blog_posts`, `case_videos`, `video_categories`, `regulations`, `knowledge_articles`, `crm_contacts`, `crm_deals` существуют, но API к ним нет.

### 1.4 🟠 Нет защиты от повторных заявок
`/crm/public-lead` создаёт запись на каждый запрос. Проверка: 75 запросов подряд с одним номером → **41 лид и 41 уведомление в Telegram**, остальные отсечены лимитом (60 в минуту на IP, `billing.service.mjs:40`). Телефон проверяется только по числу цифр, так что `00000000000` проходит. Нужна отсечка повторов (тот же телефон/Telegram за N минут) — у Avito такая логика уже есть (`cms-server.mjs:3987`), для сайта нет.

### 1.5 🟠 Сайт молча показывает пустоту, когда API недоступен (воспроизведено)
`HomeCases.tsx:56-59`, `CasesPage.tsx:71-85`, `BlogPage.tsx:18-21` — запрос, `.catch(() => {})` и пустой массив. Остановил локальный API и открыл `/cases`: заголовок «44+ проектов», ноль карточек, ни ошибки, ни кнопки «повторить». Ровно это сейчас видят посетители прода. Формы заявок устроены правильно — показывают ошибку и запасной путь в Telegram; контентные блоки — нет.

### 1.6 🟠 Процесс продолжает работать после фатальной ошибки
`server/cms-server.mjs:5121-5129` — обработчик `uncaughtException` только логирует и шлёт уведомление, но не завершает процесс. После такой ошибки состояние приложения не определено, а PM2 не перезапускает его, потому что процесс «жив».

### 1.7 🟡 Разделения прав фактически нет
`requireAdmin` используется ровно один раз (`:1121`, создание пользователей), на остальных 100 защищённых эндпоинтах только `requireAuth`. Любой пользователь с ролью MANAGER может читать CRM, править настройки (включая токены Avito) и удалять страницы.

### 1.8 🟡 Переписка чата доступна по ссылке без авторизации
`GET /crm/chat-transcript/:id` (`:2718`) отдаёт историю чата любому, кто знает идентификатор. Идентификатор — UUID, подобрать нереально, лимит запросов есть, но утечка ссылки = утечка переписки.

### 1.9 🟡 Модалка проектов теряет оформление
`src/pages/ProjectsPage.tsx:272-273` — атрибут `style` задан дважды, JSX оставляет последний, фон и рамка пропадают.

### 1.10 🟡 Падающий тест проверяет мёртвый компонент
`src/components/BottomNav.test.tsx` тестирует `src/components/BottomNav.tsx`, которого нет на сайте (живой — `layout/BottomNav.tsx`). Из-за него `npm test` красный.

### 1.11 🟡 Логи без времени
В `ecosystem.config.cjs` не задан `log_date_format`, поэтому строки в pm2-логах без отметок времени — разбирать инциденты тяжело. (Собственные записи `[public-lead]` время печатают.)

## Что проверено и в порядке

- **Авторизация.** Все админские эндпоинты возвращают 401 без токена (проверил 12 штук). Черновики CMS наружу не отдаются, `/api/kp` отдаёт только опубликованные.
- **Загрузка файлов.** Текстовый файл с именем `.png` и заголовком `image/png` отклонён: `PNG signature mismatch`. Есть лимит размера и белый список типов.
- **SQL-инъекции** исключены: только Prisma, сырых запросов нет.
- **XSS:** React экранирует вывод, `dangerouslySetInnerHTML` — одно место в библиотечном компоненте без пользовательских данных; все `target="_blank"` с `rel`.
- **Валидация CMS:** создание кейса без обязательных полей → 400, дубль слага → 409.
- **Секреты** в git отсутствуют, `.env` не отслеживается.
- **Таймеры и подписки** во фронтенде везде очищаются.
- **Ограничитель запросов** работает (после ~60 в минуту — 429).

**Шаг 1 — безопасность (полдня, правки маленькие и проверяемые):**
1. `sourcemap: false` в `vite.config.ts` + удалить старые `.map` с сервера.
2. Список доменов в CORS вместо `origin: true`.
3. Убрать пересылку любой `console.error` в Telegram, оставить явные вызовы.

5. Проверить и сменить админов в `app_users`, убрать пароль по умолчанию из `prisma/seed.mjs`.

**Шаг 2 — устойчивость:**
6. Чистка `buckets` в ограничителе (утечка памяти).
7. `uncaughtException` → завершать процесс, пусть PM2 поднимает заново.
8. `log_date_format` в PM2.
9. Отсечка повторных заявок по телефону/Telegram.

**Шаг 3 — видимые пользователю ошибки:**
10. Состояния ошибки и повтор для кейсов, блога и видео вместо пустых блоков.

12. Решить судьбу девяти сломанных разделов админки: дописать API, убрать из интерфейса или честно пометить. Начать с блога и видео — они видны на сайте.

**Шаг 4 — фундамент под дальнейшие изменения:**
